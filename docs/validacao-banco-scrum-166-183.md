# Relatório de Validação de Banco de Dados — SCRUM-166 / SCRUM-183

## 1. Escopo e Objetivo

Este documento registra a verificação prévia do catálogo PostgreSQL/Neon, a especificação da migration `20261117172500_scrum_183_fila_alertas_svo_e_material_sensivel.js`, o inventário de registros legados e as evidências de validação de integridade, constraints, índices (`EXPLAIN ANALYZE`), permissões de mínimo privilégio (`frotas_app`) e backup/restauração para ativação da agenda temporal SVO (`SCRUM-179`, `SCRUM-182` e `SCRUM-183`) e do campo `material_sensivel` nas solicitações administrativas.

---

## 2. Verificação do Estado Existente no Catálogo (Neon PostgreSQL)

Antes da execução da nova migration, foram inspecionados `knex_migrations`, `information_schema.columns`, `pg_constraint` e `pg_indexes` no banco `neondb`:

- **Objetos da `SCRUM-176` (`20261116171800_adiciona_periodo_previsto_ordens_svo.js`) confirmados e preservados intactos:**
  - `ordens_svo.inicio_previsto` (`timestamp with time zone`, `is_nullable = YES`, `default = null`);
  - `ordens_svo.fim_previsto` (`timestamp with time zone`, `is_nullable = YES`, `default = null`);
  - Constraint `chk_ordens_svo_periodo_previsto`: `CHECK ((((inicio_previsto IS NULL) AND (fim_previsto IS NULL)) OR ((inicio_previsto IS NOT NULL) AND (fim_previsto IS NOT NULL) AND (fim_previsto > inicio_previsto))))`;
  - Índice parcial `idx_ordens_svo_periodo_previsto` em `(inicio_previsto, fim_previsto) WHERE status IN ('ALOCADA', 'EM_DESLOCAMENTO')`;
  - Demais objetos de `ordens_svo` intactos: `ordens_svo_pkey (id)`, FKs `ON DELETE RESTRICT` para `solicitacoes_svo`, `veiculos`, `motoristas` e `equipes_svo`, `chk_ordens_svo_capacidade`, `uq_ordens_svo_solicitacao_ativa` e `idx_ordens_svo_veiculo_status_ativo`.

## 3. Estruturas Criadas pela Migration (`20261117172500`)

### 3.1. Coluna `ordens_svo.liberada_em` (`SCRUM-183`)
- **Definição:** `TIMESTAMPTZ NULL DEFAULT NULL` (sem FK).
- **Comportamento:** Mantém todos os registros existentes com `NULL` (sem atribuir liberação automática). É preenchida ou limpa exclusivamente pela reavaliação transacional da fila (`reavaliarFilaSvo`) sob `pg_advisory_xact_lock(166, 182)`.

### 3.3. Coluna `solicitacoes_viagem.material_sensivel`
- **Definição:** `BOOLEAN NOT NULL DEFAULT false`.
- **Comportamento:** Todos os registros existentes em `solicitacoes_viagem` receberam `false`. A coluna `solicitacoes_svo.material_sensivel` (`BOOLEAN NOT NULL DEFAULT false`) foi mantida intacta.

### 3.4. Proteção contra Rollback Destrutivo (`exports.down`)
O método `down` da migration implementa verificação explícita em bloco `DO $$ ... END $$`: caso existam registros em `alertas_atraso_svo`, ordens com `liberada_em IS NOT NULL` ou solicitações administrativas com `material_sensivel = true`, o rollback é bloqueado com `RAISE EXCEPTION`, impedindo perda silenciosa de histórico sem exportação e reconciliação prévia.

## 4. Evidências de Testes de Constraints, Índices (`EXPLAIN`) e Mínimo Privilégio

Os testes abaixo foram executados utilizando a conta restrita da aplicação (`frotas_app`) dentro de transação isolada revertida (`ROLLBACK`):

1. **Permissão DML e Identity Sequence (`frotas_app`):**
   - `INSERT INTO alertas_atraso_svo (ordem_em_atraso_id, ordem_afetada_id) VALUES (1, 2) RETURNING *` → **Sucesso** (`id: 1`).
2. **Bloqueio de Par Duplicado (`uq_alertas_atraso_svo_ordens`):**
   - Segundo `INSERT` com `(1, 2)` → **Rejeitado com código PostgreSQL `23505`** (`constraint: uq_alertas_atraso_svo_ordens`).
3. **Bloqueio de Par Igual (`chk_alertas_atraso_svo_ordens_distintas`):**
   - `INSERT` com `(1, 1)` → **Rejeitado com código PostgreSQL `23514`** (`constraint: chk_alertas_atraso_svo_ordens_distintas`).
4. **Bloqueio de FK Inexistente (`fk_alertas_atraso_svo_atrasada`):**
   - `INSERT` com `(999999, 2)` → **Rejeitado com código PostgreSQL `23503`** (`constraint: fk_alertas_atraso_svo_atrasada`).
5. **Verificação de Planos de Execução (`EXPLAIN ANALYZE`):**
   - Busca de alertas abertos por `ordem_afetada_id` (`WHERE ordem_afetada_id = 2 AND resolvido_em IS NULL`): utiliza `Index Scan` sobre **`idx_alertas_atraso_svo_abertos`**.
   - Busca de alerta pelo par `(ordem_em_atraso_id, ordem_afetada_id)`: utiliza `Index Scan` sobre **`uq_alertas_atraso_svo_ordens`**.
   - Não foram criados índices redundantes adicionais em `ordens_svo`, pois `idx_ordens_svo_periodo_previsto` e `idx_ordens_svo_veiculo_status_ativo` já cobrem o filtro de ordens ativas (`status IN ('ALOCADA', 'EM_DESLOCAMENTO')`).
